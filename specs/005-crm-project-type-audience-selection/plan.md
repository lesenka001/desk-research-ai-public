# План SPEC 005

Статус: SPEC утверждена владельцем 26 ноября 2026 года. T1–T3 реализованы;
автоматические проверки и независимое ревью T4 выполнены. PostgreSQL
и визуальная приемка остаются открытыми: [runtime.md](runtime.md). Требования: [spec.md](spec.md), задачи: [tasks.md](tasks.md).

## Границы и архитектура

Расширить существующие `crm/domain.py`, `crm/store.py`, `web/crm.py` и
`web/crm.css`. Использовать текущий JSONB-снимок `crm_dataset`, транзакции
с блокировкой и неизменяемую историю `crm_history`. Новые сервисы, LLM,
зависимости и локальный launcher не нужны. Формулы, IQR, нормализация ЦА
и правила принятия данных SPEC 004 сохраняются.

## Данные и совместимость

1. Добавить в снимок учет известных пар «аорг»/PN, отдельный от расчетных волн.
   Пополнять его при каждом импорте, включая отклоненные строки с корректными
   идентификаторами. Повтор PN в одном «аорг» не увеличивает число волн.
   Исключение/удаление записи не удаляет известную пару из истории проекта.
   Неверный или отсутствующий «аорг» не восстанавливать предположением.
2. Для прежних снимков восстановить известные пары из текущих записей,
   прежних принятых данных и всех сохраненных отчетов импорта. История хранит
   `report.rows[].data`, в том числе для исключенных строк. Ограничение списка
   истории последними 30 событиями для восстановления неприменимо.
   Повторы не размножают пары. При противоречиях исходных идентификаторов
   сохранить исходную историю, явно показать ограничение и не угадывать связь.
3. Добавить метаданные групп, привязанные к существующим «аорг» и ключу группы:
   постоянный номер и необязательное ручное название. Ключи `aliases`, исходные
   описания, решения IQR и принятые версии волн не переименовывать.
   Первоначальные номера старых групп назначить детерминированно по сортировке
   существующих ключей внутри «аорг» и сохранить один раз. Новым группам
   назначать следующий номер после максимального выданного; старые не перенумеровывать.
4. Нормализация старого снимка должна быть повторяемой без изменения результата.
   Сохранять дополнения атомарно под существующей блокировкой, без частичной
   записи и без изменения старых событий. Чтение не должно выдавать нестабильные
   номера до первого пользовательского изменения: предусмотреть одноразовую
   инициализацию снимка при первом доступе после обновления, с повторной проверкой
   версии под блокировкой. Такая запись выполняется только при будущей реализации.
5. Переименование — отдельная операция над метаданными с проверкой актуальности
   и существования группы. Пустое после удаления крайних пробелов название
   очищает подпись. Ограничить ввод 200 символами; превышение отклонять с сообщением.
   Название выводить как текст с HTML-экранированием. Сохранение и аудит атомарны.
   Использовать существующий вид события `decision` с отдельным действием
   переименования и значениями до/после; обновить отображение таких событий.
   Для инициализации совместимости использовать тот же допустимый вид события
   с отдельным техническим действием; SQL-ограничение `kind` менять не требуется.

## Представления и действия

- Общий каталог групп строить по существующим соответствиям и метаданным,
  включая группы без расчетных волн. Полные описания брать из сохраненных
  исходных текстов и истории, не из нормализованного системного ключа.
  Для группы доступны исходные варианты описаний и связанные PN со статусами.
- Отдельно выдавать тип проекта, общее число известных волн, группы ЦА
  и их расчетные сводки. Проект без расчетного IR остается доступным для
  просмотра с явным отсутствием расчета. Фильтрация списка не меняет тип.
- В карточке проверки и списке проектов показывать тип и общее число волн
  рядом с «аорг». Группу везде обозначать «ЦА N» и названием при его наличии.
- Для сопоставления не выбирать первую группу автоматически: пустое начальное
  значение, явное подтверждение, серверная проверка выбранного ключа и «аорг».
  Создание отдельной группы — самостоятельное действие.
- После решения показывать PN и группу, остальные автоматически затронутые
  волны с тем же описанием и оставшуюся необходимость проверки выброса.
- В списке проектов добавить форму задания, изменения и очистки названия.
  Она использует текущую сессию, проверку Origin и CSRF; обработка не меняет IR.

## Порядок и проверки

T1 → T2 → T3 → T4, одна задача — один отдельный коммит с `005-TN` в сообщении.
Предшествующие незакоммиченные изменения не включать в коммиты реализации;
для документов с прежними правками проверять именно добавленные изменения.

Целевые проверки: доменная логика типов и стабильности групп; совместимость
старого снимка, вся история импорта, транзакционный откат и повторная инициализация;
HTTP-сценарии выбора, переименования, доступа, CSRF и экранирования.
Полный набор перед завершением серии:
`.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v`;
проверка diff: `git diff --check`.

Провести одно независимое ревью готового diff, включая преобразование старых
данных и границы чтения истории. Это обязательная проверка совместимости данных
по глобальным правилам проекта. Проверить PostgreSQL на отдельной тестовой базе:
старый снимок → инициализация → повтор → перезапуск → переименование → откат
транзакции при ошибке. Рабочую БД для разработки не использовать. Если отдельная
PostgreSQL недоступна, явно записать непроверенную часть; mock-тесты не заменяют ее.

Ручная приемка: один проект, две ЦА, третья волна во вторую группу, новая отдельная
ЦА, отдельный спор о выбросе, ручное название, повтор импорта, перезапуск,
длинные описания и все статусы волн. Проверить обе страницы визуально.
Результаты и ограничения записать в `runtime.md` при выполнении T4.
